# Анализ: что доделать в проекте Restart B2B

Полный разбор заглушек, незавершённых мест и отличий от целевой карты (RESTART-DEV-MAP, TODO).

---

## 1. Заглушки и явные «будет позже»

| Где | Что | Как исправить |
|-----|-----|----------------|
| **BuyerLogin** (`/buyer/login`) | Текст: «Форма входа (логин/пароль или приглашение) будет подключена на следующем этапе». Кнопка ведёт на витрину без проверки. | Реализовать форму входа + проверку (JWT/session), редирект неавторизованных с `/buyer/*` на `/buyer/login`. |
| **MyLogin** (`/my/login`) | Текст: «Вход по PIN или логину (как в разделе Tools) будет подключён на следующем этапе». Кнопка «Войти (демо)» без проверки. | Форма входа (PIN/логин), сохранение сессии, защита роутов `/my/*`. |
| **BuyerRequests** | `handleExport`: `alert('Экспорт запроса … будет реализован при подключении API')`. | Реализовать вызов API `GET /api/buyer/rfqs/:id/export?format=pdf|xlsx` или клиентский генератор PDF/Excel. |
| **BuyerRequestCard** | То же для кнопок «Скачать PDF» / «Скачать Excel». | Аналогично — API или клиентский экспорт. |
| **MySettings** | Блоки «Профиль» и «Уведомления» — текст «Форма профиля будет доступна после входа», чекбоксы disabled. | После появления авторизации — формы профиля и уведомлений (как в BuyerProfile). |
| **MyDashboard** | Карточка «Новых запросов КП»: значение «—», подпись «за текущий период (после API)». | Подключить API/агрегат по RFQ и показывать число новых запросов. |

## 2. Нет бэкенда — всё в localStorage

| Данные | Где хранится | Проблема |
|--------|--------------|----------|
| Инвентарь (позиции, партии) | `restart-inventory`, `restart-inventory-meta`, `restart-inventory-batches` | При смене устройства/браузера данные теряются; нет многопользовательского доступа. |
| Кабинет покупателя (компания, пользователи, RFQ, сообщения, уведомления) | `restart-buyer-*` (company, users, rfqs, history, messages, notifications) | То же + нет реальной синхронизации с продавцом. |
| Язык интерфейса | `restart-locale` | Только для переключателя в шапке; кабинет покупателя не переведён на выбранный язык. |

**Что сделать:** ввести backend (например Hono + D1/KV по TODO), перенести чтение/запись на API, оставив localStorage только для кэша или офлайна при необходимости.

## 3. Формы без отправки на сервер

| Страница | Элемент | Сейчас | Нужно |
|----------|---------|--------|--------|
| **Home** | Секция `#quote` | Кнопки «Get a Quote» и «Request a callback» ведут на якорь, отдельной формы нет. | Форма с полями (имя, email, телефон, комментарий) и отправка на API или email. |
| **Contacts** | Блок «Request a callback» | Ссылка на `/#quote`. | Либо общая форма с главной, либо своя форма с отправкой. |
| **BuyerProfile** | Реквизиты, пользователи, уведомления | Сохранение только в localStorage через `buyerStore`. | `PUT /api/buyer/company`, `PUT /api/buyer/notifications`, CRUD пользователей через API. |
| **MyInventory** | Импорт прайса | Парсинг в браузере, запись в `inventoryStore` (localStorage). | Отправка файла или данных на API, сохранение в БД. |

## 4. Авторизация и защита роутов

- **Кабинет покупателя** (`/buyer/*`): роуты не защищены, любой может зайти. В спецификации — только роль `buyer`.
- **Мой кабинет** (`/my/*`): то же, вход «демо» без проверки.
- **Tools** (`/tools/*`): по карте — «защищённый раздел», по факту защиты нет.

**Нужно:** общий слой авторизации (контекст/провайдер), проверка при входе в `/buyer`, `/my`, `/tools` и редирект на соответствующий login при отсутствии сессии/роли.

## 6. i18n (мультиязычность)

- **Словарь:** в `src/i18n/buyerPortal.ts` есть полный набор для EN, RO, ES, DE, PL, UA, RU для кабинета покупателя.
- **Переключатель:** в шапке есть (иконка глобуса + выбор языка), выбранный язык пишется в `restart-locale`.
- **Использование в UI:** страницы кабинета покупателя и остальной сайт **не используют** этот словарь — тексты захардкожены (в основном RU/EN).
- В TODO: «i18n: EN, DE, ES, UA», «Переключатель языка в Header» — переключатель есть, подключение строк по ключам — нет.

**Нужно:** подключить `getBuyerPortalLocale(locale)` (или react-i18next) в BuyerLayout, BuyerStock, BuyerRequests, BuyerRequestCard, BuyerProfile и при необходимости на остальных страницах.

---

## 7. Мелкие технические места

- **console.warn** в `buyerStore` и `inventoryStore` при ошибках записи в localStorage — нормально для отладки; при переходе на API заменить на логирование/обработку ошибок.
- **RESTART_LOGO** и партнёры: URL с `restartsp.com` (см. `data/partners.ts`) — при смене домена или при необходимости офлайна стоит вынести в env или локальные файлы.
- **База знаний:** контент в `src/data/knowledge.ts` (статичный). По карте возможен рост и API — при необходимости вынести в CMS/API.

---

## 8. Краткий чек-лист по приоритету

1. **Backend + API:** инвентарь, кабинет покупателя (company, users, RFQ, messages), экспорт КП.
2. **Авторизация:** вход в кабинет покупателя и «Мой кабинет», защита роутов, роль `buyer`.
3. **Формы с отправкой:** Get Quote / Request callback на главной и в контактах.
4. **Экспорт КП:** реализовать PDF/Excel (серверный endpoint или клиентская генерация).
5. **i18n:** подставить строки из `buyerPortalLocales` в UI кабинета покупателя (и при необходимости всего сайта).
6. **MySettings:** после появления авторизации — формы профиля и уведомлений.
7. **Дашборд «Мой кабинет»:** блок «Новых запросов КП» считать с API.
8. **По желанию:** страницы `/marketplace/catalog`, `/marketplace/item/:id`, `/partners` по карте.

После этого можно считать текущий объём заглушек и «будет реализовано» закрытыми в пользу рабочего MVP с API и авторизацией.
